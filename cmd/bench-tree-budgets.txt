# bench-tree 预算（毫秒/档，5 次样本取中位数）。消费方：
#   php cmd/bench-tree.php --check cmd/bench-tree-budgets.txt
# 挂在本仓 CI 的 php job 与 `composer bench:tree`。
#
# 这些是干什么用的：抓**量级回归**，不是漂移。帧-rebuilt 模型下每个脏帧都要重跑
# view builder + toArray()，任何一条把它从 O(节点数) 变成 O(节点数²) 的改动
# （在树里做线性查找、每节点重算一次共享样式表、数组拷贝写成多层嵌套）都会让
# 大档从"一百多毫秒"跳到"秒级"——那正是这里要拦的东西。
# 百分级的抖动不归它管：每档预算 = 实测中位数 × ~1.25 取整。
#
# 标定（2026-10-20，本机 Apple Silicon，PHP 8.5.7，5 次取中位数）：
#   1000 行/  3001 节点   3.11ms  (min 1.51 / max 16.63)
#   2000 行/  6001 节点   （见 bench 输出）
#   5000 行/ 15001 节点  24.77ms  (min 20.25 / max 42.06)
#  10000 行/ 30001 节点  57.56ms  (min 51.42 / max 71.66)
#  20000 行/ 60001 节点 132.03ms  (min 112.65 / max 143.07)
#   us/节点 1.04 → 2.20（随规模上升：这是分配与哈希增长，不是缺陷；上限按最差档取）
#
# 为什么 µs/节点单列一条：它是唯一能跨规模比较的数。某一档看起来还行、
# 但每节点成本悄悄翻倍时，只有这一条会动——那是"每节点多走了一遍共享计算"的指纹。
#
# 内存这轮**不立门**：20k 行峰值 168MB 已超 PHP 默认 128MB，那是框架特性
# （每节点约 2.8KB），不是回归信号。bench 会打印峰值供诊断，等出现实再决定。
#
# 重标定规则（与参考项目同纪律）：某个特性让成本真实上涨时，连测 5 次，
# 把预算改成新中位数 × ~1.25，并在**同一次提交**里写清楚是哪条链路变贵了。
# 不许用"调高预算让门变绿"的方式消化一个没解释的回归。
